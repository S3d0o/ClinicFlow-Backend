## 1. Summary

P0 makes the `v2` branch safe to run on its own database. It then puts the foundation V2 builds on into the existing code:
- layer rules enforced by the build
- one organization and one default branch, with time zones
- appointment status rules inside the entity
- notifications and emails through an outbox
- an audit trail
- permission checks, health probes, a migration bundle for deployments, and CI

P0 adds no `/api/v2` endpoints. The inherited routes keep working for the V2 frontend.

## 6. Risks

- **PR 0 is V1's safety net.** Until it merges, nobody runs or migrates `v2`.
- **PRs 7 and 9 break many tests.**
  - 16 test files use appointment statuses.
  - The email and notification tests assume immediate delivery.
  - Rewrite them in the same PR; `DrainOutboxAsync()` keeps the assertions simple.
- **Seeding speed.** Without the switch in PR 10, the audit and outbox interceptors would slow the large demo seed (about 30 s today).
- **Retries re-run code.** With the execution strategy (PR 3), the code inside a transaction may run twice. That is safe once side effects go through the outbox (PR 9). Until then, the booking email must stay outside the retried block.
- **Denying edits on `AuditEntry` depends on PR 11**, because `db_owner` would bypass the `DENY`.
